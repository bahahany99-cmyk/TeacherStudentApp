# الجزء الأول: قرارات المنظومة — معتمدة في المرحلة 2

هذه القرارات اعتمدها صاحب المشروع صريحًا، وهي **ملزمة** لأي تنفيذ لاحق.

| المعرّف | القرار | الأثر العملي |
|---|---|---|
| **F-01** | **Flutter + Dart** لتطوير تطبيق **Android**. | مشروع واحد، لغة Dart، بلا كود أصلي إلا عند الحاجة لحزمة إضافات. |
| **F-02** | **Firebase هي المنظومة الأساسية** للخدمات الخلفية، و**لا Supabase** حاليًا. | لا تُضاف أي حزمة أو خدمة Supabase. |
| **F-03** | **Firebase Authentication** لتسجيل الدخول عبر **Google**. | مزوّد Google هو الوحيد المفعل في v1. |
| **F-04** | **Cloud Firestore** قاعدة البيانات الأساسية لكل البيانات: المستخدمون، ملفات المدرسين، المجموعات، الحجوزات، الرسائل، التقييمات. | لا قاعدة بيانات ثانية. تصميم المستندات والفهارس مسؤولية المشروع. |
| **F-05** | **Firebase Storage** للصور والملفات التي يسمح التطبيق برفعها. | قواعد Storage إلزامية قبل أي رفع حقيقي. |
| **F-06** | **Firebase Cloud Messaging** لإشعارات الهاتف. | الإرسال يتم من الخادم/الدوال لا من التطبيق. |
| **F-07** | **Cloud Functions** للعمليات التي تحتاج تحققًا موثوقًا، **عند الحاجة وبعد تقييم التكلفة**. | لا تُضاف دالة إلا بمبرر مكتوب وتقدير تكلفة. |
| **F-08** | **Firestore هو المسؤول عن البحث والفلاتر المنظمة** في v1: استعلامات مركبة + فهارس + تقسيم نتائج إلى صفحات. **لا محرك بحث خارجي** إلا إذا أثبتت الاختبارات لاحقًا حاجة حقيقية. | يجب تصميم حقول قابلة للفلترة (مسطّحة) وفهارس مركبة، وتجنّب البحث النصي الحر غير المدعوم. |
| **F-09** | نبدأ بالخدمات **المجانية حيث أمكن**، مع مراعاة الحصص والتكلفة عند تصميم النظام. **لا افتراض بأن كل شيء مجاني**. | تقسيم الصفحات إلزامي، تقليل المستمعين الحيّين، مراقبة الحصص، تقدير تكلفة قبل الإطلاق. |
| **F-10** | **لا مدفوعات ولا عمولات ولا محفظة** داخل التطبيق في v1. | لا حزم دفع، ولا حقول أسعار إلزامية تُحصَّل. |

# الجزء الرابع: الأمان — أساس معماري ونطاق لازم للتنفيذ

**لا شيء هنا منفَّذ أو مُختبر بعد.** ما يلي التزامات تصميمية إلزامية قبل أي إطلاق.

## 4.1 ما يجب أن تتضمنه قواعد Firestore (غير مكتوبة بعد)

1. **هوية ودور:** القواعد تقرأ دور المستخدم من مستند `users/{uid}`؛ لا يُقبل دور ممرَّر من العميل.
2. **حماية البيانات الشخصية:** المستخدم يقرأ/يكتب مستنده فقط؛ لا يعدّل مستخدم بيانات مستخدم آخر.
3. **ملفات المدرسين:** حالة `approved`/`featured` تُكتب من الإدارة فقط؛ القراءة العامة للملفات المعتمدة فقط.
4. **الحجوزات:** الطالب يقرأ طلباته، المدرس يقرأ طلباته؛ تغيير الحالة إلى `accepted` ليس من صلاحية العميل (D-08 أدناه).
5. **المحادثات:** قراءة/كتابة رسائل المجموعة مقصورة على الأعضاء المقبولين، والخاصة على طرفي الحجز — بالقواعد لا بالواجهة.
6. **التقييمات:** التحقق من أهلية المُقيِّم ومنع التكرار.
7. **رفض الكتابة المباشرة** لأي حقل مُشتق/محسوب (عدّاد السعة، التقييم المتوسط، الحالة).

## 4.2 قواعد Storage (غير مكتوبة بعد)

- قيود نوع/حجم الملف، ومسارات مبنية على `uid`/`teacherId`.
- منع الكتابة على صور مدرس آخر، ومنع رفع ملفات غير معتمدة النوع.

## 4.3 عمليات يجب أن تُنفَّذ على الخادم

1. قبول/رفض الحجوزات وحالاتها.
2. منع تجاوز سعة المجموعات (عملية ذرية).
3. التحقق من عضوية المحادثات.
4. منح/تغيير الأدوار وحالة اعتماد الملف.
5. إرسال إشعارات تغيّر الحالة.
6. تسجيل الإجراءات الإدارية (audit).

> **D-08 (مقترح، غير معتمد):** تنفيذ تغييرات الحالة الحسّاسة داخل `Cloud Functions` (قابلة للاستدعاء) بحيث لا يكتب العميل حقل الحالة إطلاقًا. يحتاج موافقة + تقدير تكلفة (F-07).

## 4.4 ممنوعات مطلقة

- لا `service account` أو مفاتيح إدارية داخل تطبيق Android.
- لا `google-services.json` ولا `firebase_options.dart` ولا `keystore` في Git (مستثناة في `.gitignore`).
- لا قواعد مفتوحة (`allow read, write: if true`) حتى في بيئة التطوير.
- لا الادعاء بأن الأمان "مكتمل" قبل كتابة القواعد واختبارها فعليًا.
