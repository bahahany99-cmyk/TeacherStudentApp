# P29 — ترحيل `accountHidden` وخطوات التشغيل الآمن

> **لا يُنفَّذ هذا الترحيل على قاعدة الإنتاج إلا بموافقة صاحب المشروع، وبعد
> قراءة ناتج المعاينة (Dry Run).** هذه الوثيقة تصف الطريق والتأكيدات، ولا
> تنفّذ شيئًا بذاتها.

## 1) ما المشكلة بدقة

كل استعلامات اكتشاف المدرسين تفلتر بمساواة صريحة:

```dart
_firestore.collection('teacherProfiles')
  .where('status', isEqualTo: 'verified')
  .where('accountHidden', isEqualTo: false)   // ← الشرط
```

في Firestore **غياب الحقل ≠ `false`** عند فلتر المساواة: المستند الذي لا يحمل
`accountHidden` لا يطابق الشرط، فلا يعود في نتيجة الاستعلام. ومع ذلك:

- **قاعدة القراءة** تسمح به: `resource.data.get('accountHidden', false) == false`
  — أي أن `get` يعامل الغياب كـ`false`.
- **المُحوِّل** `teacherProfileFromMap` يقرأه بـ`readBool` ويعامله `false` كذلك.

النتيجة: ملف «قديم» (أُنشئ خارج مسار التطبيق — وحدة تحكّم، استيراد، أو قبل
P17) بلا هذا الحقل يكون **مقروءًا بالمعرّف** و**غائبًا عن كل قائمة**. وهذا
بالضبط ما رآه صاحب المشروع: مدرس موثّق تظهر مجموعته وشارة توثيقه، بينما صفحة
المدرسين تعرض «لا نتائج» وصفّ المحافظات يفرغ (لأن مصدره نفس القائمة الفارغة).

السبب الكامل والخرائط: `docs/P29_DIAGNOSIS.md`.

## 2) حدود الترحيل (مفروضة في الكود والسكربت معًا)

| القيد | كيف فُرض |
|---|---|
| يضيف `accountHidden: false` **فقط** للمستندات التي **ينقصها** الحقل | `needsBackfill()` (السكربت) و`hasAccountHiddenFlag` (Dart) — الفحص على **وجود المفتاح** لا على قيمته |
| لا يمسّ مستندًا يحمل الحقل | مستند بـ`true` أو `false` لا يدخل قائمة العمل أصلًا |
| لا يعدّل أي حقل آخر | `batch.update(ref, { accountHidden: false })` — حقل واحد |
| لا حذف | لا `delete()` ولا `FieldValue.delete()` في أي مسار |
| معاينة قبل التنفيذ | الوضع الافتراضي معاينة؛ الكتابة تحتاج `--apply` صريحًا، ويُطبع عدد المستندات ومعرّفاتها |
| آمن للتكرار | التشغيل الثاني يجد «0 مستندًا» — لا كتابة مكرّرة |
| فشل جزئي لا يُسقط العملية | كل مستند يُعالج ويُسجّل خطؤه؛ يُعاد التشغيل على ما تبقّى |

## 3) الإصلاح البرمجي المصاحب (لا يعتمد على الترحيل)

الترحيل يعالج البيانات القديمة مرة واحدة، لكن السبب كان يتكرّر: قرار الإدارة
(`_decide`) كان يكتب الحالة وحدها. الآن:

| المسار | الملف | السلوك |
|---|---|---|
| قرار التوثيق/الرفض الإداري | `lib/data/firebase/firestore_repositories.dart` (`_decide`) + `lib/data/firebase/teacher_profile_writes.dart` | يقرأ المستند، ويضيف `accountHidden: false` **فقط عند غيابه**؛ الحقل الموجود — `true` أو `false` — لا يُمسّ (لن يعود حساب مخفي إلى الظهور) |
| حفظ صاحب الملف لملفه | نفس الموضع (`saveMyProfile`) | يضيف الحقل عند غيابه فقط عند التحديث، فتُصلح الملفات القديمة نفسها عند أول تعديل |
| إنشاء ملف جديد | موجود أصلًا منذ P17 | يكتب `accountHidden: false` عند الإنشاء |

## 4) خطوات التشغيل

### المتطلبات

- `node` (متوفّر في CI/بيئة التطوير) و`firebase-admin`:
  ```bash
  npm install --no-save firebase-admin
  ```
- حساب خدمة (Service Account) لمشروع Firebase، ومتغيّر البيئة
  `GOOGLE_APPLICATION_CREDENTIALS` يشير إلى ملف المفتاح.
  > المفتاح **لا** يُوضع في المستودع ولا في الكود ولا في سجلات.

### الخطوة 1 — معاينة (Dry Run): لا تكتب شيئًا

```bash
GOOGLE_APPLICATION_CREDENTIALS=/secure/path/service-account.json \
  node tool/migrations/backfill_account_hidden.js --project <PROJECT_ID> --verbose
```

المخرَج المتوقع: عدد المستندات المقروءة، عدد ما ينقصه الحقل، وقائمة المعرّفات
(أول 100 مع `--verbose`، أو دائمًا في وضع المعاينة). **راجع العدد قبل المتابعة.**

### الخطوة 2 — التنفيذ (بعد الموافقة فقط)

```bash
GOOGLE_APPLICATION_CREDENTIALS=/secure/path/service-account.json \
  node tool/migrations/backfill_account_hidden.js --project <PROJECT_ID> --apply
```

### الخطوة 3 — التحقق

1. أعِد تشغيل أمر المعاينة: يجب أن يقول «0 مستندًا» (اكتمال + تكرار آمن).
2. افتح التطبيق بحساب **طالب عادي** (لا صلاحيات إدارة) وافتح «المدرسون»:
   - يظهر المدرس الموثّق الذي كان غائبًا (مثال الشكوى: «Shady»).
   - صفّ المحافظات لم يبقَ فارغًا.
3. افتح مجموعته: الشارة والاسم كما كانا (لم يتغيّرا).
4. تأكد أن الحساب المخفي (إن وُجد) **ما زال مخفيًا**: لا يظهر في القائمة، لكن
   مجموعته/رابطه المباشر يعملان كما كانا.

## 5) التحقق من عدم المساس بأي شيء آخر

- المستندات التي تحمل الحقل **لم تُقرأ للكتابة أصلًا** (انظر `pending` في
  السكربت) — لا يمكن أن تتغيّر.
- الحقل المضاف `false` هو القيمة التي كانت القواعد والمُحوِّل يفترضانها غيابًا،
  فلا يتغيّر أي سلوك قراءة سابق: **لا مستند يصبح مقروءًا أو غير مقروء**، بل
  يصبح **قابلًا للمطابقة في الاستعلام** فقط.

## 6) التراجع (لو لزم)

الترحيل **إضافي بحت**، ولا يلزم تراجع تشغيلي: الأسوأ أن تختفي قيمته، لا أن
تفسد بيانات. إن أراد صاحب المشروع التراجع تمامًا فذلك يعني حذف الحقل المضاف
فقط (وليس حذف مستندات) — ويُعاد بذلك العطل الأصلي، فلا يُنصح به.

## 7) نموذج بديل داخل التطبيق

`FirestoreAccountHiddenBackfill` (`lib/data/firebase/firestore_account_hidden_backfill.dart`)
يُنفّذ نفس المنطق عبر Firestore للمسؤول، ويُختبر منطقُه عبر
`AccountHiddenBackfill` (`lib/data/migration/account_hidden_backfill.dart`)
بمستودع وهمي حتمي. حدوده: تحديث إداري من العميل يشترط أن تكون **كل** مفاتيح
المستند الناتج ضمن `adminDecisionKeys` في `firestore.rules`، فملف عليه
`isFeatured`/`featuredOrder` (مدرس مميّز) يرفضه الخادم. لذلك **الطريق الموصى
به هو سكربت Admin SDK** الذي لا يمرّ بالقواعد، ولا يمسّ أي حقل آخر.

## 8) ما لم يتغيّر في هذا الطور

- **لا** تعديل على `firestore.rules`.
- **لا** حذف أي بيانات أو حقل.
- **لا** تحسينات بحث جديدة، و**لا** تغيير لنموذج الحضور/الاتصال (`isOnline`) —
  طور لاحق بعد تأكيد إصلاح الظهور.
